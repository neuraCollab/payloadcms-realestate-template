# Лабораторная работа №4
## Метрическая оценка качества объектно-ориентированного ПО

**Цель работы:** рассчитать для собственного программного проекта метрики связности, метрики Чидамбера-Кемерера и метрики Лоренца-Кидда; выполнить анализ полученных значений и сформулировать рекомендации по улучшению.

В качестве объекта по-прежнему используется приложение «Realty», то есть кодовая база на TypeScript + React 19 + Next.js 15. Методологическая основа — ГОСТ Р ИСО/МЭК 25010-2015 (модель качества программного продукта) и классические работы Chidamber & Kemerer (1994), Lorenz & Kidd (1994).

---

## 1. Предварительное замечание о применимости

Классический набор объектно-ориентированных метрик сформулирован для языков с явными классами и наследованием — Smalltalk, C++, Java. Современный React (16.8+) опирается на функциональные компоненты и хуки; наследование как таковое отсутствует, его место занимает композиция.

Это означает, что прямое применение формул TCC, LCC, WMC и других к React-кодовой базе требует уточнения соответствий:

- **класс** — модуль (`*.tsx` или `*.ts`);
- **метод** — экспортируемая функция или компонент, плюс локально определённые хелперы и хуки;
- **поле, свойство** — переменная состояния (`useState`), пропс или модульная константа;
- **наследование** — отсутствует; ближайший аналог — композиция через render-props и children;
- **сцепление** — количество ESM-импортов из других внутренних модулей.

При такой подстановке метрики сохраняют исходный смысл — указывают на качество модульного дизайна, — но количественные пороги, выведенные исходно для Java/C++, требуют переинтерпретации.

## 2. Метрики связности по методам

### 2.1. Определения

Пусть в классе (модуле) `C` имеется `N` методов. Тогда `NP(C) = N*(N-1)/2` — общее количество пар методов. Среди них:

- `NDC(C)` — количество пар, имеющих **прямые** соединения (используют общее поле либо вызывают друг друга);
- `NIC(C)` — количество пар с **косвенными** соединениями (через цепочку других методов).

На основе этих величин определяются:

- **TCC(C) = NDC(C) / NP(C)** — Tight Class Cohesion;
- **LCC(C) = (NDC(C) + NIC(C)) / NP(C)** — Loose Class Cohesion.

Для функционального React в качестве методов учитываются: основной экспортируемый компонент, его внутренние обработчики (`onClick`, `onSubmit`) и локально определённые pure-функции.

### 2.2. Расчёт для выборки модулей

Для оценки взято пять представительных модулей:

| Модуль | Методы (N) | NP | NDC | NIC | TCC | LCC |
|---|---|---|---|---|---|---|
| `src/components/ui/button.tsx` | 1 | 0 | 0 | 0 | n/a | n/a |
| `src/components/ui/form-field.tsx` | 1 | 0 | 0 | 0 | n/a | n/a |
| `src/components/ui/star-rating.tsx` | 2 | 1 | 1 | 0 | 1.00 | 1.00 |
| `src/components/PropertyFilters/index.tsx` | 3 | 3 | 3 | 0 | 1.00 | 1.00 |
| `src/components/PropertyListingPage/index.tsx` | 4 | 6 | 4 | 2 | 0.67 | 1.00 |

TCC и LCC, близкие к 1.0, означают, что методы внутри модуля сильно связаны общими полями или вызовами. Это положительный признак модульного дизайна.

Случай `PropertyListingPage` (TCC = 0.67) требует комментария. В нём четыре «метода»: основной компонент и три pure-функции — `buildWhere`, `pickBadge`, `pickMeta`. Pure-функции не делят состояние с компонентом и не вызывают друг друга, поэтому формально дают «косвенные» пары через общий вызов из компонента. Низкий TCC здесь — следствие принятой архитектурной практики выноса чистых трансформаций из тела компонента, а не дефект.

## 3. Метрики Чидамбера-Кемерера

### 3.1. WMC — Weighted Methods per Class

Сложность каждого метода оценена цикломатической сложностью (упрощённый счёт: 1 плюс количество ветвлений `if`, тернарных операторов, `switch case`, `.map`, `.filter`).

| Модуль | Методы | Σ сложностей | WMC |
|---|---|---|---|
| `Button` (`button.tsx`) | 1 | 1 | 1 |
| `Header/Component.client.tsx` | 1 | 1 | 1 |
| `MobileNav.tsx` | 1 | 2 | 2 |
| `PropertyFilters/index.tsx` | 3 | 6 | 6 |
| `PropertyListingPage/index.tsx` | 4 | 20 | 20 |
| `PropertyDetailPage/index.tsx` | 1 | 12 | 12 |
| `ImageGallery/index.tsx` | 1 | 4 | 4 |

Граница риска по Чидамберу и Кемереру — WMC = 20. Только `PropertyListingPage` приблизился к этому значению. Основной вклад вносит функция `buildWhere`, содержащая 10 ветвлений по типам фильтров (`if (sp.city)`, `if (sp.rooms && sp.rooms !== 'all')` и так далее).

### 3.2. DIT — Depth of Inheritance Tree

В функциональном React наследование классов отсутствует. Соответствующая глубина равна нулю для всех модулей выборки. Композиция компонентов через children или render-props не учитывается в DIT в его классическом определении.

### 3.3. NOC — Number of Children

Также неприменимо в исходном виде. В качестве близкой по смыслу метрики использую число потребителей модуля — количество мест, в которых компонент импортируется.

| Компонент | Импортируется в N модулях |
|---|---|
| `Button` | 18 |
| `Input` | 6 |
| `Textarea` | 3 |
| `Label` (через `FormField`) | 2 |
| `FormField` | 2 |
| `Alert` | 2 |
| `Modal` | 2 |
| `PropertyCard` | 3 (листинг, recent, related) |
| `PropertyFilters` | 1 |
| `Logo` | 2 (`Header`, `Footer`) |

Высокая реиспользуемость `Button` и `Input` (18 и 6 соответственно) — признак того, что базовые примитивы дизайн-системы действительно работают как единая точка истины, а не дублируются по компонентам страниц.

### 3.4. CBO — Coupling Between Objects

В качестве сцепления учитывается количество ESM-импортов из внутренних модулей проекта (без учёта пакетов из `node_modules`).

| Модуль | Внутренних импортов |
|---|---|
| `Button` | 1 (`@/utilities/ui`) |
| `Header/Component.client.tsx` | 4 |
| `MobileNav.tsx` | 4 |
| `PropertyListingPage/index.tsx` | 5 |
| `PropertyDetailPage/index.tsx` | 7 |
| `RealtorReviewForm` | 5 |

Значения 4–7 — нормальный диапазон для шеллов страниц, агрегирующих несколько подкомпонентов. Низкое значение `Button` (1) подтверждает изоляцию примитива.

## 4. Метрики Лоренца-Кидда

### 4.1. CS — Class Size

Общий размер модуля считается как сумма числа операций и числа полей/состояний.

| Модуль | Операций | Состояний / полей | CS |
|---|---|---|---|
| `PropertyFilters` | 3 | 1 (`draft`) | 4 |
| `ImageGallery` | 3 | 2 (`selectedImage`, `isModalOpen`) | 5 |
| `PropertyListingPage` | 4 | 0 (server component) | 4 |
| `RealtorReviewForm` | 2 | 7 (`name`, `email`, `rating`, `comment`, `submitting`, `success`, `error`) | 9 |

Лоренц и Кидд считают значение CS > 8 кандидатом на рефакторинг. В выборке такой кандидат один — `RealtorReviewForm` (CS = 9). Причина — семь отдельных `useState` для полей формы. Эта же причина в работе №2 проявилась как дефект №1 (отсутствие inline-валидации): семь независимых состояний не дают возможности централизованно проверять корректность ввода.

### 4.2. NOO — Number of Operations Overridden

В функциональной композиции переопределение реализуется через параметры по умолчанию. Например, `<Button variant="default">` имеет дефолтный вариант, который «переопределяется» явным значением пропа. Формальное NOO в смысле наследования метода — равно нулю для всех функциональных компонентов.

### 4.3. NOA — Number of Operations Added

Применимо к компонентам, расширяющим примитив дополнительной логикой. Например, `SearchBar` поверх обычного `<input>` добавляет два метода — обработчик `onSubmit` и хранение локального состояния `internal`. NOA для `SearchBar` равно 2.

## 5. Сводный анализ

Полученные значения позволяют сделать несколько содержательных наблюдений.

**Связность модулей в проекте высокая.** TCC и LCC у проверенных модулей близки к единице. Исключения объяснимы архитектурными соображениями (вынос pure-функций за пределы компонента).

**Сцепление умеренное.** CBO примитивов дизайн-системы держится на уровне 1–4 импортов, что свидетельствует о хорошей изоляции. Шеллы страниц имеют CBO 4–7 — это нормально для агрегирующих компонентов.

**Точка повышенного риска одна.** Это `PropertyListingPage` со взвешенной сложностью WMC = 20. Функция `buildWhere` слишком ветвистая и нарушает Single-Responsibility, мапируя пять разных типов фильтров в одну `where`-структуру. Рекомендация — вынести трансформацию в файл `PropertyFilters/schemas.ts`, реализовать через таблицу маппинга:

```ts
const FIELD_TRANSFORMERS: Record<string, (v: string) => Record<string, unknown>> = {
  city: (v) => ({ 'location.city': { equals: v } }),
  rooms: (v) => v !== 'all' ? { rooms: { equals: v } } : {},
  // …
}
```

При таком подходе WMC снизится до ≈ 8, а добавление нового типа фильтра не потребует правки `PropertyListingPage`.

**Вторая точка роста — формы.** `RealtorReviewForm` имеет CS = 9 из-за семи независимых `useState`. Рекомендация — миграция на `react-hook-form` с zod-схемой; одновременно решается дефект №1 из работы №2.

**Дублирование маппинга ссылок.** Функция `resolveHref` присутствует в двух местах — `Header/Nav/index.tsx` и `Header/MobileNav.tsx`. Это формально не отображается в метриках, но повышает CBO косвенно (каждый из этих файлов импортирует одни и те же типы). Рекомендация — вынести `resolveHref` в `src/utilities/resolveCmsLink.ts`.

## 6. Выводы

В целом метрики свидетельствуют о приемлемом качестве модульной структуры проекта. Большая часть кодовой базы — это небольшие, специализированные модули с высокой связностью и низким сцеплением. Базовые примитивы дизайн-системы переиспользуются широко (`Button` — 18 модулей), что подтверждает, что архитектура «токены → примитивы → оболочки → страницы», заложенная в работе №1, действительно соблюдается.

Сформулированные на основе метрик три рекомендации (вынести `buildWhere` в схему, мигрировать формы на `react-hook-form`, вынести `resolveHref` в общий утилит) фиксируются как технический долг для следующей итерации проекта.
