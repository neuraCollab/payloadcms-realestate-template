# Лабораторная работа №2
## Ручное тестирование

**Цель работы:** на основе спецификации программного продукта подготовить набор тестовых случаев, провести ручное тестирование, зафиксировать обнаруженные дефекты и сделать выводы о качестве реализации.

Объектом ручного тестирования служит то же приложение, для которого было оформлено техническое задание в работе №1 — веб-каталог недвижимости «Realty». В качестве методологической рамки используется ГОСТ Р 56922-2016 (соответствует ISO/IEC 29119-1) — концепции и определения тестирования ПО, а также ГОСТ 19.301-79 — требования к программе и методике испытаний.

---

## 1. Спецификация на систему

### 1.1. Функциональное назначение

Веб-приложение для каталогизации, поиска и просмотра объектов недвижимости. Поддерживает четыре типа объектов (квартиры, коммерческая, участки, жилые комплексы), каждый со своей схемой полей. Интегрировано с административной CMS Payload для управления контентом.

### 1.2. Описание пользовательского интерфейса

Интерфейс приложения состоит из следующих основных экранов и элементов.

**Шапка.** Закреплена в верхней части окна, высота 64 пикселя. Содержит логотип-ссылку на главную, навигационное меню (на десктопе — горизонтальный список ссылок, активный пункт подчёркнут; на мобильном — иконка «гамбургер», открывающая выдвижную панель), переключатель темы.

**Подвал.** Содержит логотип, навигационные ссылки (пункты подтягиваются из глобальной настройки Payload `footer`), копирайт и переключатель темы.

**Главная страница.** Расположена по адресу `/`. Содержит hero-блок с поисковой строкой и чипами разделов, сетку из четырёх статистических карточек, блок «Новые предложения».

**Страница листинга.** Отображается по адресам `/flats`, `/commercial`, `/lands`, `/residential-complexes`. Включает заголовок и счётчик результатов, форму фильтров (поля зависят от типа объекта), сетку карточек, опциональную карту с маркерами и блок пагинации.

**Карточка объекта в листинге.** Состоит из обложки с бейджем сделки («Продажа» либо «Аренда»), заголовка, адреса, цены и компактной строки с основными характеристиками.

**Детальная страница объекта.** Содержит хлебные крошки (главная → раздел → объект), верхний блок с заголовком и ценой, галерею изображений с возможностью полноэкранного просмотра, описание (форматированный текст), список удобств, сайдбар с карточкой риелтора и формой отзыва, карту с местоположением.

**Форма отзыва о риелторе.** Поля: имя (обязательное), email (необязательное, не публикуется), оценка от одной до пяти звёзд (обязательная), текст отзыва (обязательный), кнопка отправки.

**Форма обращения.** Поля: тема, имя, email, текст (форматированный, на TipTap), необязательное вложение, кнопка отправки.

**Модальное окно галереи.** Изображение в полном размере, навигация стрелками, кнопка закрытия.

**Переключатель темы.** Иконка солнца либо луны в шапке и в подвале. По клику меняет атрибут `data-theme` на корневом элементе.

### 1.3. Описание вводимых параметров

В строке поиска на главной странице вводятся произвольные строковые запросы по городу, району или жилому комплексу. Выбор раздела осуществляется чипами; по умолчанию выбран раздел «Квартиры». В формах фильтрации поля зависят от типа объекта:

- квартиры: город, район, количество комнат (студия, 1, 2, 3, 4, 5+), тип сделки (продажа, аренда, посуточно), минимальная и максимальная цена;
- коммерческая: тип сделки, тип помещения (офис, торговое, склад, свободное назначение, общепит);
- участки: назначение (ИЖС, СНТ, промышленное, коммерческое), наличие коммуникаций;
- жилые комплексы: статус сдачи, тип застройки.

Форма отзыва принимает имя (строка), email (RFC 5322), оценку (целое число от 1 до 5), текст. Форма обращения принимает аналогичные поля плюс файл-вложение (изображение, PDF или Word-документ, не более 10 МБ).

### 1.4. Описание критических ситуаций

В процессе работы возможны следующие критические ситуации:

- отсутствует подключение к БД (контейнер PostgreSQL не запущен либо не отвечает);
- запрошен несуществующий объект — должна отображаться корректная страница 404;
- отправлена форма отзыва с пустыми обязательными полями;
- попытка входа в админ-панель пользователем без роли `admin`;
- размер загружаемого файла во вложении превышает 10 МБ;
- в фильтре указана пара значений, при которой минимальная цена превышает максимальную.

## 3. Классификация дефектов

Согласно ГОСТ Р 56922-2016 дефекты классифицируются по уровню критичности:

- **S1 (критический)** — блокирует основные сценарии: невозможно открыть главную, админ-панель, происходит потеря данных;
- **S2 (высокий)** — основной сценарий частично нерабочий: фильтр не применяется, форма не отправляет данные на сервер;
- **S3 (средний)** — функциональный дефект, не блокирующий работу: некорректное сообщение об ошибке, неверная подсказка;
- **S4 (низкий)** — косметический дефект: визуальное расхождение, опечатка, неточная иконка.

### Найденные дефекты

**Дефект №1 (S3).** В форме отзыва о риелторе нет inline-валидации поля email — пользователь узнаёт о неверном формате только после клика по кнопке «Отправить». Корректно с точки зрения формальной валидации, но снижает UX. Тест-кейс №17 проходит, дефект обнаружен при дополнительном исследовании.

**Дефект №2 (S4).** При переключении на тёмную тему на герое-блоке поверх фотографии текст становится плохо читаемым: исходный белый цвет был ранее заменён на `text-primary-foreground`, который в тёмной теме становится тёмным. Затрагивает один экран, не блокирует функциональность. Тест-кейс №14 формально проходит.

**Дефект №3 (S4).** При первом рендере иконка переключателя темы кратковременно (около 50 миллисекунд) показывается некорректной для текущей темы — гидратация компонента происходит позже применения темы. Тест-кейс №15 проходит, дефект заметен только при медленном соединении.

## 5. Анализ результатов и рекомендации

Результаты тестирования показывают, что основная функциональность реализована корректно — все сценарии категорий smoke и functional проходят без ошибок. Дефекты сосредоточены в области UX-полировки.

Для устранения обнаруженных проблем рекомендую:

1. Внедрить библиотеку `react-hook-form` совместно со схемами `zod` во все формы. Это даст единообразную inline-валидацию и одновременно снизит сложность компонентов форм (см. лабораторную работу №4 по метрикам).
2. Для оверлеев поверх изображений ввести отдельный токен цвета `text-on-image`, который остаётся белым в обеих темах, и заменить им `text-primary-foreground` на героях.
3. Обернуть компонент `ThemeToggle` в обёртку с отложенным рендером, чтобы избежать мигания иконки при гидратации; либо реализовать применение иконки полностью через CSS (на основе `[data-theme]`).

Кроме того, для дальнейшего расширения покрытия следует подготовить отдельные тест-кейсы для нестандартных сценариев: загрузка файла во вложении формы обращения, поведение карты при отсутствии координат, поведение при разрыве соединения с базой данных. Эти случаи требуют отдельной инфраструктуры (chaos-тестирование) и в рамках текущей работы не покрыты.
