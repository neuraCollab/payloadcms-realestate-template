# Лабораторная работа №1
## Разработка технического задания

**Цель работы:** оформить техническое задание на собственный программный продукт по структуре, установленной ГОСТ 19.201-78 «Единая система программной документации. Техническое задание. Требования к содержанию и оформлению».

В качестве объекта взят мой pet-проект — веб-приложение каталога недвижимости «Realty», над которым я работаю в учебных целях с прицелом на возможное использование в небольшом риелторском агентстве. Технический стек проекта: Next.js 15, Payload CMS 3, PostgreSQL 15, Tailwind CSS. Код размещён на GitHub (`neuraCollab/payloadcms-realestate-template`) и развёртывается через Docker Compose.

---

## 1. Введение

### 1.1. Наименование программы

«Realty» — веб-приложение каталога объектов недвижимости с административной панелью управления контентом.

### 1.2. Краткая характеристика области применения

Программа разрабатывается для риелторских агентств и онлайн-сервисов поиска недвижимости. На текущей стадии — учебный продукт; в дальнейшем не исключается коммерческое применение в качестве шаблона или готового решения для малого риелторского бизнеса.

Программа предоставляет:

- публикацию объектов четырёх типов (квартиры, коммерческая недвижимость, земельные участки, жилые комплексы);
- фильтрацию, поиск и просмотр на карте;
- управление контентом редакторами через веб-интерфейс без участия разработчика;
- интеграцию с почтой и формами обратной связи.

---

## 2. Основания для разработки

Разработка ведётся в рамках самостоятельной работы по дисциплине «Качество и тестирование ПО» и в качестве портфолио-проекта. Внешнего заказчика на текущей стадии нет.

Прообразом интерфейса послужил публичный шаблон Realestic (`realestic.framer.website`), который был использован как ориентир по компоновке страниц без копирования авторского контента.

---

## 3. Назначение разработки

**Функциональное назначение.** Размещение, поиск и просмотр объектов недвижимости в сети Интернет с возможностью самостоятельного управления каталогом сотрудниками агентства.

**Эксплуатационное назначение.** Работа в режиме круглосуточного доступа на сервере под управлением Linux, с возможностью администрирования из любой точки через защищённое HTTPS-соединение. Конечные пользователи — анонимные посетители сайта, контент-менеджеры и риелторы с разграничением ролей.

---

## 4. Требования к программе

### 4.1. Требования к функциональным характеристикам

Программа должна обеспечивать следующие функции.

**4.1.1. Каталог объектов недвижимости.** Поддерживается четыре отдельные коллекции (квартиры, коммерческая, участки, жилые комплексы), каждая со своей схемой полей. Доступен листинг с фильтрацией по основным параметрам (тип сделки, цена, площадь, количество комнат, район) и сортировкой по дате публикации.

**4.1.2. Детальная страница объекта.** Содержит галерею изображений с возможностью полноэкранного просмотра, описание (форматированный текст), таблицу характеристик, удобства, информацию о риелторе, форму отзыва о риелторе, карту с местоположением.

**4.1.3. Главная страница и контентные страницы.** Главная содержит поисковую строку, набор быстрых фильтров по разделам, статистические карточки с количеством активных объектов, блок последних предложений. Помимо этого пользователю доступны страницы «О компании», «Команда», «Блог», «Контакты», собранные редактором из готовых блоков в админ-панели.

**4.1.4. Поиск.** Полнотекстовый поиск по объектам и постам блога, реализованный через плагин `@payloadcms/plugin-search`.

**4.1.5. Карта объектов.** На базе библиотеки Leaflet с подложкой OpenStreetMap/Yandex Maps. Объекты отображаются маркерами с попапами; набор маркеров соответствует текущему фильтру.

**4.1.6. Административная панель.** Доступна по адресу `/admin`. Поддерживает CRUD-операции над всеми коллекциями, управление глобальными настройками (header, footer), Live Preview при редактировании страниц, разграничение прав по двум ролям — `admin` и `realtor`.

**4.1.7. Формы.** Реализованы три формы: обратной связи (Payload Form Builder), отзыва о риелторе с пятизвёздочной оценкой и подробного сообщения с прикреплением файла. Все формы валидируют обязательные поля на клиенте и на сервере.

**4.1.8. Светлая и тёмная темы.** Переключатель темы в шапке и подвале; выбор сохраняется в `localStorage` и применяется до первого рендера через скрипт `InitTheme` (предотвращает мигание).

### 4.2. Требования к надёжности

Время восстановления после сбоя контейнера приложения — не более одной минуты, что обеспечивается политикой `restart: unless-stopped` в Docker Compose. Целостность данных гарантируется транзакционной моделью PostgreSQL. Резервное копирование БД и медиафайлов выполняется ежесуточным cron-скриптом (`db/backup.sh`), полная архивная копия выгружается на удалённое объектное хранилище.

В режиме разработки горячая перезагрузка (HMR) не должна терять введённые пользователем данные в формах — данные хранятся в React-состоянии до момента отправки.

### 4.3. Условия эксплуатации

Программа работает на сервере с доступом в сеть Интернет. Размещение шифрованного трафика обеспечивается reverse-proxy Caddy с автоматическим получением сертификата Let's Encrypt. Климатические и температурные условия определяются техническими требованиями серверного оборудования и находятся вне зоны ответственности программного продукта.

Регламентное обслуживание сводится к обновлению зависимостей через `pnpm install` не реже одного раза в квартал и установке обновлений безопасности операционной системы.

### 4.4. Требования к составу и параметрам технических средств

Минимальная конфигурация сервера:

| Параметр | Минимум | Рекомендация |
|---|---|---|
| Процессор | 2 vCPU | 4 vCPU |
| ОЗУ | 2 ГБ | 4 ГБ |
| Дисковое пространство | 25 ГБ SSD | 50 ГБ SSD |
| Операционная система | Ubuntu 22.04 LTS / Debian 12 | Ubuntu 22.04 LTS |
| Среда выполнения | Docker 20+, Docker Compose v2 | Docker 24+, Compose v2.20+ |

На стороне клиента поддерживаются все современные браузеры с поддержкой ECMAScript 2022: Chromium 110+, Firefox 110+, Safari 16+, Edge 110+.

### 4.5. Требования к информационной и программной совместимости

Node.js версии 18.20.2 и выше либо 20.9.0 и выше. PostgreSQL 15 или более новая. Менеджер пакетов pnpm 10. Совместимость HTTP-API обеспечивается через REST-интерфейс Payload, формат данных — JSON. Сайт пригоден для индексации поисковыми системами благодаря server-side rendering, выгрузке sitemap и мета-тегам Open Graph.

### 4.6. Специальные требования

Требуется поддержка русского языка как в UI, так и в контенте, а также корректная обработка кириллических URL-сегментов. Внешний вид должен соответствовать принципам Material 3 с акцентом на минимализм и единый набор токенов (цвет, типографика, форма, тень). Адаптивность — обязательное требование: брейкпоинты 640 и 1024 пикселя по ширине, мобильное меню реализуется как выдвижной drawer на основе компонента Dialog из библиотеки Radix UI.

Доступность интерфейса — минимальная высота интерактивных элементов 40 пикселей, видимые focus-кольца, корректная ARIA-разметка для модальных окон и групп переключателей.

## 6. Технико-экономические показатели

Поскольку проект учебный, экономические показатели не нормируются. Контролируемые параметры:

- объём кодовой базы — 281 файл TypeScript/TSX, около 3300 строк в директории `src/components/`;
- время сборки production-бандла — не более 3 минут (`pnpm build`);
- размер production-образа Docker — не более 500 МБ;
- стоимость аренды сервера — не более 1000 ₽/мес при выбранной конфигурации.

## 7. Стадии и этапы разработки

Разработка проходит следующие стадии:

1. оформление настоящего технического задания;
2. эскизный проект и согласование дизайна на основе принципов Material 3;
3. реализация дизайн-системы — токены и базовые UI-примитивы;
4. реализация общих оболочек (шапка, подвал, карточка объекта, фильтр);
5. реализация страниц и наполнение контентом;
6. тестирование — ручное, автоматизированное, метрическая оценка качества;
7. подготовка документации и развёртывание на сервере.

## 8. Порядок контроля и приёмки

Контроль качества выполняется по следующим критериям:

- проверка типов через `pnpm exec tsc --noEmit` — в новом коде ошибок типов быть не должно;
- линтинг через `pnpm lint` — все правила проходят;
- сборка `pnpm build` — выполняется без ошибок;
- автоматическое тестирование через Playwright — все сценарии из лабораторной работы №3 проходят;
- ручная приёмочная проверка — последовательный обход маршрутов `/`, `/flats`, `/commercial`, `/lands`, `/residential-complexes`, `/posts`, `/about`, `/contact`, `/agents`, `/blogs`, а также страницы администрирования `/admin`.
