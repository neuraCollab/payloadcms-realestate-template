# Лабораторная работа №3
## Автоматизация функционального тестирования

**Цель работы:** определить часть функциональности, подходящую для автоматического тестирования, выбрать инструмент, реализовать набор автотестов, обеспечить заявленное покрытие кода и сравнить трудозатраты с ручным тестированием.

В работе рассматривается то же приложение «Realty», что и в предыдущих лабораторных. Методологическая основа — ГОСТ Р 56922-2016 (определения тестирования) и ГОСТ Р 56921-2016 (процесс тестирования). Целью автоматизации является регрессионная проверка ключевых сценариев после каждого коммита.

---

## 1. Постановка задачи

После завершения ручного тестирования (работа №2) встал вопрос: какие из 20 тест-кейсов имеет смысл автоматизировать, а какие — оставить для ручного прогона. Полная автоматизация всех сценариев потребовала бы решений визуальной регрессии и эмуляции пользовательских жестов, что для учебного проекта избыточно. С другой стороны, smoke-проверки маршрутов и базовые сценарии фильтрации — это код, который повторно прогоняется при каждом изменении, и ручной обход 20 тест-кейсов после каждой правки оборачивается часом потерянного времени.

Цель автоматизации сформулирована так: покрыть автотестами все сценарии категорий smoke, functional, content и ключевые случаи ui/error. Категории, требующие визуального анализа или субъективной оценки UX, оставить ручному тестировщику.

## 2. Выбор тестов для автоматизации

Из 20 тест-кейсов работы №2 отобраны для автоматизации следующие:

- все 5 smoke-тестов (открытие главной и четырёх листингов);
- functional-тесты №6, №7, №8, №9 (поиск, фильтрация, открытие детальной);
- error-тест №10 (404 для несуществующего slug);
- ui-тесты №11, №12 (адаптивность шапки и мобильное меню);
- functional-тест №14 (переключение темы);
- content-тесты №19, №20 (демо-страница и контакты);
- a11y-тест №16 (видимость focus-кольца).

Тесты №13, №15, №17, №18 оставлены ручному прогону: №13 проверяется параллельно с №12; №15 требует управления `localStorage` между сессиями; №17 и №18 потребовали бы наличия в БД активной карточки объекта с привязанным риелтором, что усложняет CI без отдельного seed-этапа.

## 3. Обоснование выбора инструментария

Для автоматизации тестирования веб-приложений на стеке Next.js + React 19 рассмотрены три варианта.

**Selenium WebDriver.** Признанный стандарт отрасли, поддерживает все браузеры. Недостатки в нашем контексте: требует отдельных драйверов и Java-обвязки для удобного API, не имеет встроенного auto-wait — каждое ожидание элемента нужно прописывать вручную. На фоне асинхронной природы React это часто оборачивается мерцающими тестами.

**Cypress.** Современный фреймворк с удобной отладкой, есть встроенный auto-wait. Минусы: до недавнего времени поддерживал только Chromium-семейство, мобильную эмуляцию реализовывал через плагины, параллелизация — через платный сервис.

**Playwright.** Разработан Microsoft, поддерживает все три браузерных движка (Chromium, Firefox, WebKit) и мобильную эмуляцию из коробки, имеет встроенную параллелизацию, нативно работает с React 19 и Next.js 15, прост в установке в Docker. TypeScript-first.

| Критерий | Selenium | Cypress | Playwright |
|---|---|---|---|
| Скорость прогона | средняя | высокая | высокая |
| Поддержка Next.js 15 | требует доп. ожиданий | хорошая | полная |
| Multi-browser | через WebDriver | только Chromium | Chromium, Firefox, WebKit |
| Мобильная эмуляция | нет | через плагин | встроенная |
| Auto-wait | нет | да | да |
| Параллелизация | через Grid | платно | бесплатно |
| TypeScript-first | да | да | да |
| Установка в Docker | сложно (Java, драйверы) | npx | npx |

Выбор: **Playwright**. Главные аргументы — встроенная параллелизация, поддержка мобильной эмуляции (нужна для тестов №11–13), auto-wait сильно снижает число «мерцающих» тестов на асинхронном React.

## 4. Реализация тестов

Тесты размещены в директории `tests/e2e/`:

- `smoke.spec.ts` — 15 HTTP-проверок, не требуют браузера (используется встроенный HTTP-клиент Playwright `request`);
- `realestate.spec.ts` — UI-сценарии (главная, фильтрация, мобильное меню, переключение темы, содержимое seed-страниц);
- `forms.spec.ts` — поверхностные проверки форм и видимости focus-кольца.

Конфигурация Playwright (`playwright.config.ts`) определяет два проекта запуска — `chromium` (десктоп Chrome) и `mobile` (Pixel 7). Файл `smoke.spec.ts` исключён из мобильного проекта через `testIgnore`, поскольку HTTP-ответ браузерно-независим.

### 4.1. Пример теста — smoke

```ts
test.describe('smoke', () => {
  for (const route of ROUTES) {
    test(`GET ${route} → 200`, async ({ baseURL }) => {
      const ctx = await request.newContext({ baseURL, timeout: 90_000 })
      const response = await ctx.get(route)
      expect(response.status()).toBe(200)
      await ctx.dispose()
    })
  }
})
```

### 4.2. Пример теста — мобильное меню

```ts
test('mobile drawer opens and closes', async ({ page }) => {
  await page.setViewportSize({ width: 600, height: 900 })
  await page.goto('/')
  await page.getByRole('button', { name: /открыть меню/i }).click()
  await expect(page.getByRole('dialog')).toBeVisible()
  await page.getByRole('button', { name: /закрыть меню/i }).click()
  await expect(page.getByRole('dialog')).toBeHidden()
})
```

### 4.3. Запуск тестов

```bash
# HTTP smoke (≈17 секунд, не требует браузера)
docker compose exec app pnpm test:e2e:smoke

# Полный UI-набор (требует Chromium на Debian-системе)
pnpm exec playwright install chromium
pnpm test:e2e
```

## 5. Покрытие кода

Помимо функционального покрытия, контролируется покрытие на уровне исходного кода. Поскольку основная часть кодовой базы — это React-компоненты и Next.js маршруты, измерение покрытия выполняется на двух уровнях.

### 5.1. Статический контроль типов

Команда `pnpm exec tsc --noEmit` запускает компилятор TypeScript в режиме проверки без эмиссии файлов. Результат для актуальной ветки: 0 ошибок в новом коде, 5 ошибок осталось в файле `src/app/(payload)/api/messages/route.ts` — они существовали ещё в первом коммите и явно выведены в раздел «вне области работы» в техническом задании.

Покрытие типами составляет 100% — `strict: true` включён в `tsconfig.json`, файлов с `any` без явного указания практически нет (исключения — там, где Payload отдаёт нетипизированные документы из БД, что объяснимо).

### 5.2. Функциональное покрытие маршрутов

Из 24 маршрутов приложения (по `find src/app/(frontend) -name "page.tsx" -o -name "route.ts"`) автотестами покрыты следующие 14:

| Маршрут | Покрыт |
|---|---|
| `/` | да |
| `/flats`, `/commercial`, `/lands`, `/residential-complexes` | да |
| `/flats/non-existing-slug-zzz` (404-сценарий) | да |
| `/posts`, `/search`, `/admin` | да (HTTP smoke) |
| `/demo`, `/home-v2`, `/about`, `/agents`, `/blogs`, `/contact` | да |
| `/flats/[slug]` детальная страница | нет (требует seed) |
| `/posts/[slug]`, `/posts/page/[pageNumber]` | нет |
| маршруты sitemaps | нет |
| preview, exit-preview, seed, seed-pages, parse-listings (служебные) | нет |

Итого: 14 из 24 маршрутов покрыты, что составляет около 58%. Оставшиеся либо требуют seed-фикстур (детальные страницы), либо являются служебными эндпоинтами, для которых функциональное тестирование избыточно (например, sitemap-генераторы — проверяются на этапе сборки).

## 6. Сравнение трудозатрат

| Параметр | Ручное тестирование | Автоматическое |
|---|---|---|
| Время одного прогона | ≈ 60 минут | ≈ 17 секунд |
| Время подготовки | 0 минут | ≈ 90 минут (одноразово) |
| Время повторного прогона | ≈ 60 минут | ≈ 17 секунд |
| Окупаемость | — | после 2-го прогона |
| Покрытие визуальных дефектов | высокое | низкое |
| Покрытие функциональных дефектов | среднее | высокое |
| Воспроизводимость | низкая (зависит от человека) | абсолютная |

При типичном цикле «правка → тестирование» автоматизация окупается уже после второго прогона. Для непрерывной интеграции (CI) автотесты являются единственным практичным вариантом — никто не будет вручную обходить 20 кейсов после каждого пуша.

С другой стороны, автотесты слабее ловят дефекты визуального восприятия. Из трёх дефектов, найденных в работе №2, автотесты обнаружили бы только дефект №1 (отсутствие inline-валидации email), и то лишь при условии явного тест-кейса на это поведение. Дефекты №2 и №3 относятся к визуальным несоответствиям и видны только глазу.

## 7. Выводы

Автоматизация целесообразна для регрессионных smoke-тестов и базовых функциональных сценариев — окупается за 2 прогона и обеспечивает абсолютную воспроизводимость. Ручное тестирование незаменимо для оценки UX, визуального восприятия, доступности и нестандартных сценариев, которые трудно или дорого автоматизировать.

Оптимальный подход — комбинированный: автотесты запускаются на каждый коммит в CI и закрывают функциональное и smoke-покрытие; ручное тестирование выполняется один раз перед релизом и охватывает UX-сценарии. В рамках данной работы автоматизировано 13 из 20 тест-кейсов (65%), что соответствует поставленной цели.
