## 1. ПР1. Разработка технического задания (ГОСТ 19.201-78)

### 1.1. Введение

**Наименование программы:** «Realty» — веб-каталог объектов недвижимости с административной панелью управления контентом.

**Краткая характеристика области применения:** программа предназначена для риелторских агентств и онлайн-сервисов поиска недвижимости. Обеспечивает публикацию объектов четырёх типов (квартиры, коммерческая недвижимость, земельные участки, жилые комплексы), их фильтрацию, поиск и просмотр на карте, а также управление контентом редакторами через административную панель.

### 1.2. Основания для разработки

Разработка ведётся в рамках учебной работы по дисциплине «Качество и тестирование ПО». Прообразом является шаблон [Realestic Framer](https://realestic.framer.website/).

### 1.3. Назначение разработки

**Функциональное назначение:** размещение, поиск и просмотр объектов недвижимости в сети Интернет. Управление каталогом редакторами без участия разработчика.

**Эксплуатационное назначение:** работа в режиме 24×7 на сервере под управлением Linux или Windows, доступ для пользователей — через любой современный веб-браузер.

### 1.4. Требования к программе

#### 1.4.1. Требования к функциональным характеристикам

Программа должна обеспечивать:

**а) Каталог объектов недвижимости:**
- листинги четырёх коллекций: «Квартиры» (`/flats`), «Коммерческая» (`/commercial`), «Участки» (`/lands`), «Жилые комплексы» (`/residential-complexes`);
- фильтрацию по типу сделки, цене, площади, количеству комнат, городу и району; URL параметры синхронизируются с состоянием формы;
- отображение карточки объекта с обложкой, ценой, адресом, ключевыми характеристиками;
- детальную страницу объекта с галереей, описанием, удобствами, картой и формой связи с риелтором.

**б) Главную страницу:**
- поисковую панель с автодополнением;
- быстрые фильтры по разделам (квартиры, коммерция, участки, ЖК) в виде чипов Material 3;
- статистические карточки с количеством активных объектов в каждом разделе;
- блок «Новые предложения» — последние четыре опубликованных объекта.

**в) Информационные страницы**, формируемые редактором из блоков в админ-панели Payload: главная-альтернатива (`/home-v2`), «О компании» (`/about`), «Команда» (`/agents`), «Блог» (`/blogs`), «Контакты» (`/contact`).

**г) Блог:**
- листинг постов (`/posts`) с пагинацией;
- индивидуальную страницу поста (`/posts/[slug]`).

**д) Поиск:** полнотекстовый поиск по объектам и постам (`/search`).

**е) Карту объектов:** на основе Yandex/OSM плиток с маркерами и попапами; отображает результаты текущего фильтра.

**ж) Административную панель Payload CMS** (`/admin`):
- управление коллекциями (объекты, агенты, отзывы, посты, медиа, формы);
- управление глобальными настройками (header, footer);
- режим Live Preview при редактировании страниц;
- разграничение прав по ролям (`admin`, `realtor`).

**з) Формы:**
- форма обратной связи (Form Builder Payload);
- форма отзыва о риелторе с оценкой 1–5;
- форма сообщения с прикреплением файла и редактором TipTap.

**и) Светлая и тёмная темы** (тёмная — заглушка), выбор сохраняется в `localStorage`.

#### 1.4.2. Требования к надёжности

- Время восстановления после сбоя контейнера приложения — не более 1 минуты (Docker `restart: unless-stopped`).
- Целостность БД обеспечивается транзакциями PostgreSQL и резервным копированием через `db/backup.sh`.
- Резервная копия может быть восстановлена скриптом `db/restore.sh` без потери целостности связанных коллекций (`--clean --if-exists`).
- HMR-перезагрузка в режиме разработки не должна терять данные пользователя (формы сохраняют состояние в React-стейте до отправки).

#### 1.4.3. Условия эксплуатации

- Доступ — через сеть Интернет/локальную сеть по протоколу HTTPS (HTTP в режиме разработки).

## 2. ПР2. Ручное тестирование

### 2.1. Спецификация на систему

#### 2.1.1. Функциональное назначение

Веб-приложение для каталогизации, поиска и просмотра объектов недвижимости. Поддерживает четыре типа объектов с раздельными коллекциями и схемами фильтров; интегрировано с административной CMS Payload для управления контентом.

#### 2.1.2. Описание пользовательского интерфейса

Интерфейс содержит следующие основные экраны и элементы:

- **Шапка** (sticky, высотой 64 px): логотип-ссылка на главную, навигационное меню (десктоп — горизонтальный список ссылок с подчёркиванием активного маршрута; мобильный — гамбургер-кнопка, открывающая drawer), переключатель темы.
- **Подвал**: логотип, навигационные ссылки (Payload `footer` global), копирайт, переключатель темы.
- **Главная страница** (`/`): hero с поисковой строкой и чипами разделов, сетка статистических карточек, блок «Новые предложения».
- **Страница листинга** (`/flats`, `/commercial`, `/lands`, `/residential-complexes`): заголовок и счётчик результатов, форма фильтров, сетка карточек объектов, карта (если доступны координаты), пагинация.
- **Карточка объекта** в листинге: обложка с бейджем сделки («Продажа»/«Аренда»), заголовок, адрес, цена, мета-строка (комнаты/этаж/площадь).
- **Детальная страница объекта**: хлебные крошки, заголовок и цена в карточке, галерея изображений, описание (rich text), удобства, сайдбар с информацией о риелторе и формой отзыва, карта.
- **Форма отзыва о риелторе** (`RealtorReviewForm`): поля «Имя» (обязательно), «Email» (опционально, не публикуется), оценка 1–5 (звёзды), текст отзыва (обязательно), кнопка отправки.
- **Форма обращения** (`RichMessageForm`): тема, имя, email, текст (rich-text TipTap), вложение, кнопка отправки.
- **Модальное окно галереи**: изображение в полном размере, навигация стрелками, кнопка закрытия.
- **Переключатель темы**: иконка солнце/луна, переключает атрибут `data-theme="dark|light"` на `<html>`.

#### 2.1.3. Описание вводимых параметров

- **Поиск (`/`)**: текстовое поле «Город, район, ЖК…», селектор раздела (chips: Квартиры, Коммерческая, Участки, ЖК), кнопка «Найти».
- **Фильтр объектов**: поля схемы зависят от типа:
  - Квартиры: `city`, `district`, `rooms` (studio/1/2/3/4/5+), `transactionType` (sale/rent), `minPrice`, `maxPrice`.
  - Коммерческая: `transactionType`, `commercialType` (office/retail/warehouse/free-purpose/catering).
  - Участки: `landType` (residential/agricultural/industrial/commercial), `hasUtilities` (yes/no).
  - ЖК: `status`, `type`.
- **Форма отзыва**: имя — строка, email — RFC 5322, оценка — 1–5, текст — строка.
- **Форма обращения**: тема — строка, имя — строка, email — RFC 5322, текст — HTML, файл — JPG/PNG/PDF/DOC/DOCX ≤ 10 МБ.

#### 2.1.4. Описание критических ситуаций

1. Отсутствие подключения к БД (PostgreSQL контейнер не запущен или не отвечает).
2. Запрос несуществующего объекта (`/flats/non-existing-slug`) — должна показываться страница 404.
3. Ввод в форму отзыва пустых обязательных полей.
4. Отправка формы при отсутствии связи с сервером.
5. Вход в админ-панель без прав (`role` не `admin`).
6. Слишком крупный загружаемый файл во вложении.
7. Превышение `maxPrice` < `minPrice` в фильтре (логически некорректная пара).

### 2.3. Категории дефектов

В соответствии с ГОСТ Р 56922-2016 дефекты разделяются на:

- **Критический (S1)** — блокирует основные сценарии (нельзя открыть главную, /admin, потеря данных).
- **Высокий (S2)** — основной сценарий частично нерабочий (фильтр не применяется, форма не отправляет).
- **Средний (S3)** — функциональный дефект, не блокирующий (некорректное сообщение об ошибке, неверная иконка).
- **Низкий (S4)** — косметический (визуальное расхождение, опечатка).

### 2.5. Анализ и рекомендации

1. Дефект S3 «inline-валидация email» — внедрить `react-hook-form` + `zod` в формы для единообразной валидации.
2. Дефект S4 «тёмная тема на героях» — заменить `text-primary-foreground` на семантически корректный `text-white` для оверлеев поверх изображений (или ввести токен `text-on-image`).
3. Гидратационная вспышка иконки темы — обернуть `ThemeToggle` в `<NoSSR>` либо подавлять рендер до завершения `useEffect`.

## 4. ПР4. Метрическая оценка качества

### 4.1. Адаптация метрик к функциональному React

Классические метрики Чидамбера-Кемерера и Лоренца-Кидда сформулированы для классических ОО-языков. В современном React-приложении большинство «классов» заменены функциональными компонентами и хуками. Адаптация:

- **Класс** ↔ модуль (`*.tsx` или `*.ts`).
- **Метод** ↔ экспортируемая функция/компонент или вспомогательный хук.
- **Свойство/поле** ↔ переменная состояния (`useState`), пропс, или модульная константа.
- **Наследование** ↔ композиция: один компонент «обёртывает» другой через children/render-props.
- **Зависимости (CBO)** ↔ количество ESM `import`-выражений.

### 4.2. Расчёт метрик связности по методам

Для оценки взяты пять представительных модулей:

| Модуль | Методы (M) | NDC | NIC | TCC | LCC |
|---|---|---|---|---|---|
| `src/components/ui/button.tsx` (Button) | 1 | 0 | 0 | n/a (M < 2) | n/a |
| `src/components/ui/form-field.tsx` (FormField) | 1 | 0 | 0 | n/a | n/a |
| `src/components/ui/star-rating.tsx` (StarRating) | 1 + 1 inner | 1 | 0 | 1.0 | 1.0 |
| `src/components/PropertyFilters/index.tsx` | 3 (компонент, `apply`, `useEffect`-handler) | 3 | 0 | 1.0 | 1.0 |
| `src/components/PropertyListingPage/index.tsx` | 4 (component, `buildWhere`, `pickBadge`, `pickMeta`) | 4 | 2 | 0.67 | 1.0 |

Высокие TCC/LCC ≈ 1.0 — признак хорошо связных модулей. Низкий TCC у `PropertyListingPage` объясняется тем, что вспомогательные функции `pickBadge`/`pickMeta` не делят состояние с основным компонентом — это нормальный паттерн pure helpers.

### 4.3. Метрики Чидамбера-Кемерера

#### 4.3.1. WMC (Weighted Methods per Class)

Сложность каждого метода оцениваем цикломатической сложностью (упрощённо — 1 + количество ветвлений). Замеры по выборке:

| Модуль | M | Σ сложностей | WMC |
|---|---|---|---|
| `Button` (button.tsx) | 1 | 1 | 1 |
| `Header/Component.client.tsx` | 1 | 1 | 1 |
| `MobileNav.tsx` | 1 | 2 (1 useEffect + 1 map) | 2 |
| `PropertyFilters/index.tsx` | 3 | 1+3+2 | 6 |
| `PropertyListingPage/index.tsx` | 4 | 1+10+5+4 | 20 |
| `PropertyDetailPage/index.tsx` | 1 | 12 | 12 |
| `ImageGallery/index.tsx` | 1 | 4 | 4 |

**WMC > 20** считается границей риска. Только `PropertyListingPage` приближается к ней — в основном из-за `buildWhere`, который содержит 10 ветвлений по типам фильтров. Рекомендация — вынести `buildWhere` в `PropertyFilters/schemas.ts` и сделать table-driven.

#### 4.3.2. DIT (Depth of Inheritance Tree)

В функциональном React наследования нет; используется композиция. DIT ≡ 0 для всех модулей. Компонент `<PropertyListingPage>` композирует `<PropertyCard>`, `<PropertyFilters>`, `<PropertyMap>` — это не наследование, а связь use.

#### 4.3.3. NOC (Number of Children)

Аналогично — n/a для функционального React. В качестве близкой по смыслу метрики используется **число потребителей модуля** (количество мест, импортирующих компонент):

| Компонент | Импортируется в N модулях |
|---|---|
| `Button` | 18 |
| `Input` | 6 |
| `Textarea` | 3 |
| `FormField` | 2 (две формы) |
| `Alert` | 2 |
| `Modal` | 2 |
| `PropertyCard` | 3 (listing, recent, related) |
| `PropertyFilters` | 1 |
| `Logo` | 2 (Header, Footer) |

Высокая реиспользуемость `Button`, `Input` — признак здоровой дизайн-системы.

#### 4.3.4. CBO (Coupling Between Object classes)

В виде количества внешних import-выражений на модуль:

| Модуль | Import-зависимостей |
|---|---|
| `Button` | 4 (react, slot, cva, cn) |
| `Header/Component.client.tsx` | 7 |
| `MobileNav.tsx` | 9 |
| `PropertyListingPage/index.tsx` | 8 |
| `PropertyDetailPage/index.tsx` | 11 |
| `RealtorReviewForm` | 7 |

CBO 7–11 — нормально для шеллов страниц. Низкий CBO примитивов (`Button` — 4) подтверждает их инкапсуляцию.

### 4.4. Метрики Лоренца-Кидда

#### 4.4.1. CS (Class Size)

| Модуль | Операций | Свойств/состояний | CS |
|---|---|---|---|
| `PropertyFilters` | 3 | 1 (`draft` state) | 4 |
| `ImageGallery` | 3 (component, `next`, `prev`) | 2 (`selectedImage`, `isModalOpen`) | 5 |
| `PropertyListingPage` | 4 | 0 (server component) | 4 |
| `RealtorReviewForm` | 2 (component, `handleSubmit`) | 7 useState | 9 |

`RealtorReviewForm` имеет 7 useState — кандидат на рефакторинг в `useReducer` или `react-hook-form` для снижения CS.

#### 4.4.2. NOO (Number of Operations Overridden)

В React-композиции — переопределение реализуется через пропсы по умолчанию. Например, `<Button variant="default">` имеет default-вариант, который «переопределяется» через явный пропс. Формальный NOO = 0 для функциональных компонентов.

#### 4.4.3. NOA (Number of Operations Added)

Применимо к компонентам, которые «расширяют» базовый примитив дополнительной логикой. Например, `<SearchBar>` добавляет 2 операции (`onSubmit` обработчик, локальный state) поверх стандартного `<input>`. NOA = 2.

### 4.5. Вывод и рекомендации

1. **Сильные стороны кодовой базы:**
   - Высокая связность модулей (TCC/LCC ≈ 1.0).
   - Низкий CBO у дизайн-примитивов, высокая реиспользуемость (`Button` импортируется в 18 модулях).
   - Глубина композиции ограничена 2–3 уровнями.

2. **Точки роста:**
   - `buildWhere` в `PropertyListingPage` (WMC=10 фрагмент) — вынести в schema-driven маппер в `PropertyFilters/schemas.ts`.
   - `RealtorReviewForm` (CS=9 из-за 7 useState) — мигрировать на `react-hook-form` + `zod`-схему. Это снизит CS до ≈3 и одновременно решит S3-дефект из ПР2.
   - Дублирование маппера `resolveHref` между `Header/Nav/index.tsx` и `Header/MobileNav.tsx` — вынести в `src/utilities/resolveCmsLink.ts`.
